**Researched:** 2026-03-30

## Summary

Phase 04.2 is a visual-only redesign of Level 2. The rocket launch-tower setting is fully replaced by a lighthouse at open sea. No gameplay logic, collision mechanics, hazard code, or level height values change. Every line of work touches either `src/background.js` (rocket rendering functions removed, lighthouse rendering added) or `PixelArt/backgrounds/level2_see/` (new PNG assets drawn and exported). `src/platforms.js` gets one small change: the L2 placeholder color block is replaced with a lighthouse-themed sprite renderer once assets exist.

The rocket system in `background.js` is self-contained in three functions (`_drawL2Elements`, `_drawL2Scaffolding`, `_drawL2Sun`) and ten constants/variables. Every rocket Image reference sits at the top of the file as module-level `const`. Removing them is clean — nothing outside `background.js` depends on rocket constants. The sun (`_bgL2Sun`) and sea launchpad (`_bgL2Landing`) are candidates for review but are not rocket-specific; the sun is reusable, and the launchpad may need replacement with a sea/rocks base.

The lighthouse design mirrors the rocket structurally: a base element at world y=0, a repeating mid-section tile up to `GameState.levelGoalY`, and a top cap. The same tiling loop pattern used for the rocket shaft can be reused verbatim — only the image references and draw constants change.

**Primary recommendation:** Strip all rocket code in one focused wave, then draw and wire new assets in a second wave. Never mix asset drawing with code refactoring.

### Tiling architecture for the new lighthouse

The lighthouse follows the identical vertical tiling pattern used for both the rocket (L2) and the shaft (L3). This pattern is proven and has no known issues:

```
world y = 0         → base image (sea shore / rocks at base of lighthouse)
world y = -tileH    → first mid tile
world y = -2*tileH  → second mid tile
...until goalY
world y = goalY     → top cap (lighthouse lantern room, snapped to last tile)
```

Code skeleton for `_drawL2Lighthouse` (mirrors `_drawL2Elements` structure):

```javascript
function _drawL2Lighthouse(ctx, camShift) {
  if (!_bgL2LhBase.complete   || _bgL2LhBase.naturalWidth   === 0) return;
  if (!_bgL2LhMid.complete    || _bgL2LhMid.naturalWidth    === 0) return;
  if (!_bgL2LhTop.complete    || _bgL2LhTop.naturalWidth    === 0) return;

  const cs    = Math.round(camShift);
  const goalY = (GameState.levelGoalY !== undefined) ? GameState.levelGoalY : -5000;

  // Sea base + lighthouse ground floor — drawn once at world y=0
  ctx.drawImage(_bgL2LhBase, 0, cs);

  // Lighthouse shaft — tile upward from above base to level goal
  for (let wy = -_LH_MID_H; wy > goalY - _LH_MID_H; wy -= _LH_MID_H) {
    const sy = wy + cs;
    if (sy > BG_H)           continue; // below viewport
    if (sy + _LH_MID_H < 0) break;    // above viewport — done
    ctx.drawImage(_bgL2LhMid, 0, sy);
  }

  // Lighthouse top (lantern room) — snap to last tile top edge
  const lastTileWy = -(Math.ceil(-goalY / _LH_MID_H)) * _LH_MID_H;
  const topScrY    = Math.round(lastTileWy + cs) - _LH_TOP_H;
  if (topScrY < BG_H && topScrY + _LH_TOP_H > -BG_H) {
    ctx.drawImage(_bgL2LhTop, 0, topScrY);
  }
}
```

Where `_LH_MID_H` is the content height of the lighthouse mid-section sprite (to be measured from the final PNG via PIL alpha-scan or manual inspection). `_LH_TOP_H` is the content height of the top sprite.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Vertical seam elimination between tiled images | Custom blend or offset logic | The `_RKT_MID_H` / `_LH_MID_H` content-height pattern already in the codebase |
| Viewport culling for off-screen tiles | Manual distance checks | The `continue` / `break` pattern in the existing tiling loop — reuse verbatim |
| Image load guard | Polling or promises | The `img.complete && img.naturalWidth > 0` guard pattern already in every draw function |
| Sprite sheet sub-region extraction | Manual pixel math | PIL alpha-scan approach (documented in background.js) — measure once, hard-code constants |

## Common Pitfalls

### Pitfall 1: Orphaned Image references cause 404 console noise
**What goes wrong:** The five rocket `const _bgL2*` Image objects at the top of `background.js` are created with `new Image()` and their `.src` is set immediately on module load. Even if the draw functions are never called, the browser fires network requests for all five files.
**Why it happens:** ES module-level code runs unconditionally on script load.
**How to avoid:** When removing a rocket Image declaration, also remove the `const _bgL2* = new Image()` line. Do not just remove the draw call.
**Warning signs:** 404 errors in browser DevTools Network tab for rocket PNG paths after the refactor.

### Pitfall 2: Forgetting to remove `_drawL2Scaffolding` from the call chain
**What goes wrong:** `_drawL2Elements` calls `_drawL2Scaffolding` as its first step. If only `_drawL2Elements` is renamed/replaced but `_drawL2Scaffolding` is left orphaned, it causes no runtime error (it simply never gets called), but it is dead code that still loads two scaffolding images.
**How to avoid:** Delete both functions together. Grep for both names before closing the task.

### Pitfall 3: Top-cap snap formula — wrong tile height constant breaks the seam
**What goes wrong:** The rocket uses `_RKT_MID_H = 270` in the snap formula. If the lighthouse mid-section sprite has a different content height and `_LH_MID_H` is estimated rather than measured, the top cap lands with a visible gap or overlap.
**Why it happens:** The snap formula `-(Math.ceil(-goalY / _LH_MID_H)) * _LH_MID_H` requires the exact content pixel height, not the image file height.
**How to avoid:** Measure `_LH_MID_H` from the final PNG using PIL or Pixelorama's canvas info. The content height is from the first non-transparent row to the last non-transparent row.

### Pitfall 4: Drawing lighthouse in world-space but forgetting to account for camShift
**What goes wrong:** If a new draw call uses a hardcoded screen Y instead of `wy + cs`, the element will not scroll with the camera.
**Why it happens:** All level-specific background elements use `camShift` (= `-cameraY`) to convert from world space to screen space. This is not CSS positioning; it is manual world-to-screen math.
**How to avoid:** Every `ctx.drawImage` for a background element that should scroll must include `+ cs` or `+ Math.round(camShift)` in the y position.

### Pitfall 5: sea_launchpad.png reuse conflict
**What goes wrong:** The current `sea_launchpad.png` shows a rocket-era sea dock. If it is kept and a lighthouse base is drawn on top, they may visually conflict at the ground level.
**How to avoid:** Plan explicitly whether the new `lighthouse_base.png` replaces `sea_launchpad.png` entirely, or whether both are drawn (launchpad behind, lighthouse in front). The simplest clean solution is to have `lighthouse_base.png` be a full 480x640 image covering the entire ground level — launchpad is then not drawn at all in L2.

### Pitfall 6: imageSmoothingEnabled must stay false
**What goes wrong:** Any new `ctx.drawImage` call for a scaled lighthouse sprite will appear blurry if `imageSmoothingEnabled` is accidentally reset to `true`.
**Why it happens:** `ctx.save()` / `ctx.restore()` do not reliably preserve `imageSmoothingEnabled` across all browsers (noted in `STYLE_GUIDE.md`).
**How to avoid:** Do not rely on save/restore for this setting. It is set once at canvas init in `main.js` and never overridden. All new draw calls inherit it correctly — just don't add `ctx.imageSmoothingEnabled = true` anywhere.

## Asset Design Guidance (for Pixelorama work)

### Sprite dimensions

All level-background sprites must be **480px wide** to cover the full canvas. Height is flexible but must be consistent within a set (base / mid / top):

- `lighthouse_base.png` — 480x640 (full-canvas, same as L3 shaft tiles)
- `lighthouse_mid.png` — 480x~300 recommended (content height = `_LH_MID_H`; design for ~250–300px of visible content to match rocket's 270px step; shorter = more tiles = more seams)
- `lighthouse_top.png` — 480x~300 (top of lighthouse, lantern room)

### Palette constraint (from STYLE_GUIDE.md — HIGH confidence)

All assets must use only the 16-color palette defined in `docs/STYLE_GUIDE.md`. Key relevant colors for a lighthouse setting:

| Role in lighthouse | Palette slot | Hex |
|-------------------|-------------|-----|
| Stone/brick body | BG-4 (mid-bg tone) | #c8a07a |
| Shadow areas | BG-2 (sky dark) | #2e3a5c |
| Sea water | WATER-1 | #2a5fa8 |
| Wave highlights | WATER-2 | #5090d0 |
| Sky reference | BG-1 | #7eb8c9 |
| Accent (light beam) | BG-3 (cloud highlight) | #ffd4a3 |

No new colors may be introduced. The lighthouse must be built from existing palette slots.

### Source resolution

Draw at **64x64 tiles** as per style guide, but background sprites (non-sprite-sheet) are drawn at their natural canvas dimensions (480px wide). The 64x64 rule applies to the character sprite and collectibles, not to the large background panels. Background panels are drawn at whatever natural pixel size covers the canvas correctly.

## Open Questions

1. **Does `sea_launchpad.png` get replaced or covered?**
   - What we know: It currently shows a rocket-era sea dock/landing pad.
   - What's unclear: Whether the imagery clashes with a lighthouse base, or can coexist if the lighthouse base is drawn transparently in the dock area.
   - Recommendation: Create `lighthouse_base.png` as a full 480x640 image that completely covers the ground. Do not draw `sea_launchpad.png` in L2 once the lighthouse base exists. This is the cleanest removal path.

2. **How wide should the lighthouse tower be?**
   - What we know: The rocket shaft was 74px wide (`_RKT_DRAW_X = 204` to `204+74=278`), centered on x=241. A lighthouse is wider and more architectural.
   - Recommendation: Draw the lighthouse as part of the full-width background image (not a narrow centered column). This eliminates the `_RKT_DRAW_X` centering hack entirely.

3. **Rocky ledge platform sprites — Phase 04.2 or Phase 5?**
   - What we know: ASSET_LIST.md assigns L2 platform sprites to Phase 5. The four success criteria for Phase 04.2 list it as optional ("L2 platform sprites reflect new setting").
   - What's unclear: Whether visual coherence requires them now or whether the green placeholder is acceptable during testing.
   - Recommendation: Draw a basic rocky ledge sprite in Phase 04.2 so the level looks complete when testing the lighthouse. If time is short, defer — the placeholder does not break any success criterion.

4. **_LH_MID_H value — depends on final sprite height**
   - What we know: This constant cannot be determined until the lighthouse_mid.png is drawn and measured.
   - Recommendation: Measure it from the final exported PNG. Planner should include a task step that reads the pixel dimensions after export and sets the constant accordingly.
